# PostPlus 1.0.0

PostPlus 1.0.0 brings the existing mail, multi-domain, Webmail and administration
features into the first stable major release, and moves the production network
transport to official PACE 0.1.1. Existing public APIs, configuration fields and
on-disk data formats remain compatible.

## Changes

- Replace production Asio networking with the unmodified PACE 0.1.1 package:
  TCP listeners and connections, UDP, hostname resolution through c-ares,
  reactor readiness, deadlines and cancellation. Internal RPC clients now use
  PACE's HTTP/1 client. Asio remains only as an independent peer in TLS tests.
- Run synchronous application handlers in bounded worker pools while one PACE
  reactor per process owns network operations. Connection deadlines cover the
  full operation, including fragmented reads and DNS/connect retries; shutdown
  cancels active I/O and joins workers.
- Preserve HTTP header-first authorization, Host/CSRF checks, strict framing,
  request limits and streaming backups through the existing PostPlus HTTP
  server over PACE transport.
- Preserve TLS 1.2+, certificate and hostname verification, STARTTLS, per-domain
  SNI and reusable IMAP IDLE polling through an OpenSSL adapter on PACE sockets.
  Server contexts use a bounded cache that reloads changed certificate/key pairs;
  a broken optional certificate affects only its matching hostname.
- Expand network regression coverage for IPv6, absolute deadlines, cancellation,
  concurrent connections, certificate rotation and TLS records split across
  IMAP IDLE polling intervals.

The 1.0.0 feature baseline includes persistent mailboxes and delivery queues,
SMTP submission and delivery, POP3 and the documented IMAP workflows, basic spam
scoring with optional Rspamd/ClamAV integration, verification code/link detection,
Webmail, scoped API keys, browser setup, backups and supervised updates. A server
can host independent mailbox domains with DNS verification, per-domain Webmail
bindings and TLS certificates, a designated administration hostname, and an
optional shared Webmail login. These capabilities retain their documented scope;
see [protocol support](https://github.com/TabNahida/PostPlus/blob/v1.0.0/docs/protocols.md)
and [operating limits](https://github.com/TabNahida/PostPlus/blob/v1.0.0/README.md#current-scope).

## Network integration and performance

The PACE migration covers the production transport and RPC client. PostPlus still
uses its own HTTP server policy and OpenSSL TLS adapter. Further adoption of
PACE's high-level server/TLS APIs depends on upstream
[asynchronous HTTP admission (#12)](https://github.com/TabNahida/PACE/issues/12),
[safe per-connection cancellation (#13)](https://github.com/TabNahida/PACE/issues/13),
and [reusable TLS input polling (#14)](https://github.com/TabNahida/PACE/issues/14).
See the [integration details](https://github.com/TabNahida/PostPlus/blob/v1.0.0/docs/pace-migration.md).

The short Windows loopback comparison against 0.5.2 showed **no overall
performance improvement**. Three-round median throughput changed by -39.7% for
HTTP health requests, -14.9% for authenticated mailbox requests, +10.7% for storage
RPC, and -3.9% for SMTP durable acceptance. RPC results varied substantially, so
its higher median does not establish a stable gain. Both backends completed
7,140 measured operations without errors and delivered all 264 SMTP messages,
including warmup. These measurements describe this PostPlus integration; they
do not establish PACE's standalone performance or sustained server capacity.
The [benchmark report](https://github.com/TabNahida/PostPlus/blob/v1.0.0/docs/pace-benchmark.md)
includes latency, raw results, methodology and limitations.

## Upgrading

PostPlus **0.3.1 and newer** can update directly to 1.0.0. Configuration, accounts,
mail, queues and existing certificate files are preserved. No configuration or
data migration is required for the network backend change. Follow the
[upgrade guide](https://github.com/TabNahida/PostPlus/blob/v1.0.0/docs/updates.md)
and retain a current backup before updating an existing installation.

The 0.5.2 hostname compatibility behavior remains: installations without an
explicitly configured administration hostname keep compatibility access.
Adding a domain does not automatically enable login hostname isolation. Review
**Domains → Login addresses** when enabling restrictions or binding `@a.com`
mailboxes to a hostname such as `mail.a.com`. Publish the corresponding DNS
records and install or request a certificate covering that hostname in the
domain's TLS section. Shared Webmail login remains optional and disabled by
default.

Existing default TLS certificates and per-host SNI overrides retain their
roles. Certificate issuance still requires the certificate authority's DNS and
HTTP-01 reachability checks; automatic certificate renewal is not implemented.
Saving certificate configuration applies it through the supervisor restart flow;
independently launched services require a manual restart. A reverse proxy that
terminates HTTPS must also have a valid certificate for its public hostname.

The first-run wizard continues to configure one mail domain. Add further domains
through **Domains** and verify their DNS before activation. Version 0.5.1 remains
a prerelease; use the stable 1.0.0 release for upgrades.
