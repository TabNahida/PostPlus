# PostPlus 1.0.1

PostPlus 1.0.1 fixes upgrades incorrectly blocked after a domain DNS check, adds
individual service restarts in administration and the API, and reduces selected
networking overhead. Configuration and stored mail remain compatible with 1.0.0;
the network dependency remains the unmodified PACE 0.1.1 package.

## Changes

- Update preparation and application now use the same runtime configuration
  comparison as settings. Saving domain DNS verification results no longer
  triggers the incorrect "configuration not applied" block. Actual runtime
  changes still require application before updating.
- **Restart and shutdown** groups all ten modules with individual restart
  controls, impact descriptions, confirmation and progress. Restart authentication,
  storage, filtering, transfer, delivery, SMTP, POP3, IMAP, Webmail or administration
  independently through the native supervisor, including under systemd.
- The API accepts `POST /api/admin/restart` with
  `{"mode":"service","service":"smtp"}`. Individual restarts preserve readiness
  checks, maintenance exclusion and rollback handling. Apply any pending runtime
  configuration first. Restarting a dependency briefly interrupts its consumers;
  restarting administration requires signing in again. See the
  [restart API](https://github.com/TabNahida/PostPlus/blob/v1.0.1/docs/api.md#restarting-services).
- Avoid redundant socket creation and repeated peer-address lookups. Combine
  small HTTP headers and bodies into one write; complete small plaintext responses
  initiate graceful close on the network reactor with bounded input draining.
- Fix a connection-capacity handoff race exposed by the faster response path.
  Each listener permits one accepted connection to wait up to 200 ms for a
  completed session's slot while keeping active and queued worker limits intact.
- Improve provisioning failure diagnostics and retain structured service logs
  in failed CI/package artifacts. Restart polling tests cover temporary
  authentication unavailability and bounded timeout behavior.

## Performance and upstream follow-up

A Windows loopback A/B/B/A comparison against 1.0.0, with six measured rounds per
version, completed **14,280 operations per version without errors** and delivered
all **528 SMTP messages per version**, including warmup. Median throughput changed
by **+46.6%** for HTTP health, **-2.5%** for authenticated mailbox requests,
**+17.9%** for storage RPC and **+3.3%** for SMTP durable acceptance.

These results do **not** establish an overall or production performance gain:
all round ranges overlap, mailbox throughput and p95 worsened, and SMTP p99 also
worsened. The short local runs do not establish sustained capacity or gains for
TLS, Linux or macOS. The
[full report and raw evidence](https://github.com/TabNahida/PostPlus/blob/v1.0.1/docs/pace-performance-followup.md)
include earlier contrary measurements and the methodology.

An independently reproduced PACE HTTP-client delay after receiving a complete
`Connection: close` response was reported as
[PACE #15](https://github.com/TabNahida/PACE/issues/15). This release reduces
PostPlus's contribution to that delay; it does not include an upstream PACE fix.

## Upgrading

PostPlus **0.3.1 and newer** can update directly to 1.0.1. Existing configuration,
accounts, mail, delivery queues and certificates are preserved; no data migration
is required. Follow the
[upgrade guide](https://github.com/TabNahida/PostPlus/blob/v1.0.1/docs/updates.md)
and keep a current backup.

**When upgrading from 0.5.2 or 1.0.0:** the already-running updater still contains
the DNS false-positive bug. If it reports unapplied configuration after checking
DNS, choose **Restart and shutdown → Restart all services**, sign in again, and
prepare/apply the update before checking DNS again. If the block persists,
resolve any actual pending runtime settings first. Once 1.0.1 is running, DNS
verification alone no longer blocks updates.

Individual restarts require the native supervisor. Existing hostname bindings,
optional shared Webmail login and per-domain TLS behavior are unchanged.
